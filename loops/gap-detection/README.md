# Loop 1 — gap detection

**Consumer: you, reading `$EVE_HOME/proposals/gaps-<date>.md`, and the memories you write because of it.**

That is the entire consumer list. If two review cycles go by and you have neither written a memory nor run `--ignore` in response to this report, the loop no longer has a consumer and you should turn it off. There is a bright line here, not a judgement call: a report nobody acts on is not a low-value report, it is a defect.

**Producer:** the recall hook, which appends one line to `state/whiffs.log` whenever a substantive prompt retrieved nothing.

Install this one first. It is the only loop whose signal is free — every prompt already generates it, so the marginal cost of collecting it is a `printf` on the path that was going to do nothing anyway. The other two loops need you to write something extra before they have anything to read.

## What it does

A retrieval that returns nothing is not a failure. It is the store telling you what it does not know, in the exact words you used to ask. Collect those, keep the ones that recur, and you have the highest-signal to-do list in the system: not what you thought you should document, but what you actually kept reaching for and not finding.

The report has three parts:

- **Open gaps** — single terms above threshold that no memory covers.
- **Recurring question shapes** — pairs of terms that whiffed together. A pair is much closer to the question you were actually asking than either word alone, and it is what you should write the memory against.
- **Probably already closed** — terms that whiffed before but that retrieval now answers, usually because you wrote the file last week. Reported so the list shrinks instead of nagging.

## Run it

```sh
# read-only, prints the report, writes nothing
$EVE_HOME/loops/gap-detection/eve-gap-detect.sh --dry-run

# write the proposal file
$EVE_HOME/loops/gap-detection/eve-gap-detect.sh

# a gap you have decided is not worth documenting
$EVE_HOME/loops/gap-detection/eve-gap-detect.sh --ignore "backfill"
```

`--ignore` is what makes this converge. Without a way to say "I have considered this and the answer is no", every report contains every gap you already declined, forever, and you stop reading it.

Options: `--since DAYS` (default 30), `--min-hits N` (3), `--min-days N` (2), `--no-probe`, `--out FILE`.

The two thresholds do the real work. `--min-hits` alone will promote a term you typed three times in one frustrated afternoon; `--min-days` requires the question to have come back on a different day, which is the difference between a passing curiosity and a hole in the store.

## Failure mode this loop is prone to

**It is the easiest loop in the system to turn into a write-only producer.** The log grows on its own, the reports look substantial, and reading one feels like progress. Nothing about it changes unless a human writes a file. Two defences are built in: `--ignore`, so declining a gap is a recorded action rather than a decision you re-make every week, and thresholds high enough that a report with no rows is the normal outcome once the store has caught up.

See [the worked example in `docs/04-loops.md`](../../docs/04-loops.md) for what this looks like when it goes wrong at scale.

## Two bugs found while building this, both worth knowing

**The report was confidently empty on macOS for a while.** The stopword list was written as one quoted paragraph spanning several lines and passed to `awk -v`. The `awk` that ships on macOS rejects a `-v` value containing a literal newline; the aggregation died on every run, `stderr` went to `/dev/null`, and the report printed "None above threshold" in the same tone it uses for a genuinely clean store. The fix was two lines of shell. The lesson was structural, and it is now enforced in the script: **if the input had usable lines and the analysis produced no records, refuse to report a result at all.** A loop that says "all clear" when it has crashed is worse than a loop that crashes, because the first one gets believed.

**Clustering on whole-prompt signatures clustered nothing.** Signing each whiff with its full sorted term set is the tidier design and it produces a table where every row has a count of one, because two phrasings of the same question never share all their words. Pairs recur. The subsequent bug was in the fix: capping at six terms *after* an alphabetical sort silently discarded every late-alphabet word, which undercounted "webhook" by more than half while never once dropping "backfill". The cap now runs on order of appearance and only the pair's name is sorted.

Both bugs produced plausible, well-formatted, wrong output. Neither produced an error.
